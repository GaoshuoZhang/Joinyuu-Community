# 企业代办收费功能模块 · 设计方案（v3.1）

状态：**修订设计稿，尚未实现，不代表发布或模块验收通过**。修订日期：2026-10-31。保留 §10 已记录的五项业务决策；按[首轮评审](enterprise-agency-fee-design-review-2026-10-31.md)补齐资金模型、并发、退款、权限及存量兼容。复审记录见本文 §13；第三轮独立复审通过后已合并 4 条 P3 文字完备性备忘（N1–N4），详见评审文件第三轮章节。

## 0. 目标与范围

社区可对企业注册、财税服务、工商变更、资质许可分别配置免费、固定费用、人工报价。首次受理确定费用，用户在线支付；未付款不阻塞受理、补件和办结。办理状态与资金状态独立，不新增“已支付”办理状态。

- 四类服务均纳入本期，全部使用社区运营方单一 PaymentMerchantConfig，不做分账。
- 不做自动计价、发票、对账单导出、电子合同及渠道逐笔对账下载。查询支付结果不等于完成渠道账单对账。
- 原稿“多收退差额”的目标保留：**代办部分退款作为本期新增资金能力**，不是现有能力。只为 agency_service 开放，其他来源保持原全额退款约束。
- 不新增用户自助退款申请入口；运营人员发起、另一位有权限的管理员审批。用户可以查看退款进度。
- 本期代办收款只走微信支付（含有权限的后台 Native）。暂不接入线下收款登记、零元改价、单独免单、追加收费或退款后重新收费。通用接口也必须执行这些限制。
- 本稿中的新模型、字段、路由、权限码和状态均为**待实施契约**，不得当成当前已有能力。当前约定仍为暂不发布。

## 1. 当前能力与改造边界

源码核对基线：API 4d61a54、后台 eb038ab、移动 Web 8c62091、小程序 7da1424。

| --- | --- | --- |

| CommerceRefund | 全额退款、异人审批、结果轮询 | 对代办新增部分/多次退款和剩余可退额度；其他来源仍全额退款 |
| 客户端收银台 | 上层处理归属、环境、OpenID 绑定/授权、调起和查询 | 复用上层编排，扩展代办来源，不能仅转发底层 appPayment |

COMMERCE_MODULES 增加 agency；客户端交易来源增加 agency_service。来源注册应集中声明：定价入口、归属校验、渠道能力、开关、超时、展示、退款和通知链接。新增来源不能默认落入租约开关或租约下单路径。代办不开放通用 quotes/orders 自由建单入口，其订单只能由受理事务建立；通用 bills/:id/orders 不得将代办转成 lease_bill。

## 2. 配置与首次费用决定

### 2.1 服务标识与配置

| serviceType（存储/配置后缀） | route（API/UI） | 申请编号前缀 |
| --- | --- | --- |
| registration | registration | EA |
| finance_tax | finance-tax | TE |
| business_change | business-change | BR |
| license | license | LA |

每服务四项配置，字段后缀统一用 serviceType，禁止把 finance-tax 与 finance_tax 混用：

| 字段 | 取值与约束 |
| --- | --- |
| agencyFeeMode_<serviceType> | free / fixed / manual；默认 free |
| agencyFeeAmountFen_<serviceType> | 安全整数，0–100000000 分；fixed 必须 >0，其他模式忽略 |
| agencyFeeTitle_<serviceType> | 去首尾空白后 1–64 字符 |
| agencyFeeRefundPolicy_<serviceType> | ≤500 字符；收费模式必填，并保存到报价快照 |

manual 在**首次受理动作内**填写金额（1–100000000 分）和报价说明（1–500 字符），不是受理完成后再报价。固定费用受理确认页也必须显示将收金额和政策。配置保存按完整服务组原子校验，提供配置版本；首次受理锁定/校验对应版本，过期的受理确认返回 409，刷新后重新确认。

配置迁移为四服务填入各自默认标题；默认免费时退款政策可空，切为收费前必须补齐，避免全局配置保存因缺少默认标题而失败。

配置变化只影响**尚未形成首次费用决定**的申请。已有免费决定不补收，已有收费决定不被新配置覆盖。改价不改变原退款政策、标题或首次模式，本期只改变金额并记录原因。

### 2.2 首次决定必须覆盖免费与历史申请

新增共享业务元数据模型 EnterpriseAgencyFeeDecision；这不是新账本，也不承担支付/退款资金事实。采用模型而非只依赖时间线，以便唯一约束、并发控制和补偿恢复：

| 字段组 | 要求 |
| --- | --- |
| 唯一归属 | UNIQUE(serviceType, applicationId)，关联申请人 userId；服务端校验正确申请表及归属 |
| 初始决定 | initialMode、配置版本、受理人/时间、首次政策快照、legacyReason；创建后不覆盖 |
| 资金关联 | billId 唯一可空；free 必为空，收费必须有账单和一对一订单 |
| 并发控制 | quoteVersion（收费初值 1）、editState（stable/repricing/attention）、activeChangeId 可空 |

申请 payload 不保存付款状态/金额；申请时间线只保存用户可见报价事件及关联 ID。账单 amountFen 是当前应收金额真源，Decision 的初始配置快照仅为审计资料，不能用于当前扣款。

部署迁移先为已有受理记录（包括已办结、受理后驳回/重提等）建立 legacy_free 决定，不追溯收费；legacy_free 是初始免费决定的原因，非第四种收费模式。以可信 accept 事件与状态核对，缺失/无法确定的历史单保守标记 legacy_free 并列入迁移报告，禁止根据当前配置补收。确认从未受理的历史 pending 申请才在下一次受理时使用新配置。无改动地先升级结构与回填、再开放收费配置，迁移可重复执行。

### 2.3 首次受理及再受理事务

两个接入点必须同时改造：

- 企业注册：POST /api/admin/enterprise-agency/registrations/:id/accept。
- 三项扩展服务：POST /api/admin/enterprise-services/:service/applications/:id/accept。

统一调用共享费用服务，保留原 DTO、动态服务权限、申请行锁与状态校验。首次受理的同一数据库事务完成：

1. 锁申请，核对 pending、用户及服务类型；读取已有 Decision。
2. 已有 Decision 时沿用其免费/收费决定，不重新报价，不再要求 manual 金额。首次决定时校验配置版本与报价参数。
3. 新建 Decision。收费同时创建 CommerceBill 与 CommerceOrder，关联申请、申请人及报价版本；免费不建账单/订单。
4. 追加首次 fee_decision/quote 事件、审计及站内通知记录，再将申请转 processing。任一步失败整体回滚；不在事务内请求微信渠道。

businessKey = agency:<serviceType>:<applicationId>；重提不更换 key。订单 buyerType=user、buyerId=申请人 UID、createdBy=申请人 UID，受理管理员另存为 createdByActor/快照操作人，不能当成订单归属人。表单中企业名称不代表允许该企业其他成员付款或查看申请。

使用 Idempotency-Key（UUID）和请求摘要持久化 accept 结果；同键同请求重放原响应，不重复报价/通知；同键不同内容 409。并发不同键按申请锁和当前状态拒绝或复用已完成结果，不产生第二份资金关联。后续合法补件重提再受理使用新操作键，但沿用同一 Decision。 accept 幂等沿用共享 AppIdempotencyKey（24 小时窗口，过期原位重认领）；超窗的同键重放因申请已非 pending 且 Decision 唯一约束兜底返回 409，资金安全不受影响，此窗口差为已知取舍。

## 3. 账单、订单与有效期

收费关系固定为：申请 → 一份 Decision → 一张 Bill → 一份 Order → 多次 Payment 尝试 → 各成功付款的 Refund。Bill、Order 中保存 serviceType、applicationId、用户、标题、退款政策、quoteVersion 和正确的业务跳转链接；sourceId 为申请 ID。

- Bill 必填 period 使用“单次代办”，sourceName 使用服务名与办理编号，不放身份证、联系电话等资料。
- Bill 的 dueDate 改为可空；代办为 null，表示未约定缴费截止日，不显示逾期。其他来源保持已有必填规则，逾期统计必须排除 null。
- Order 的 expiresAt 改为可空；代办为 null，其他来源仍由服务校验非空并维持现有 TTL。同步数据库迁移、DTO、序列化、查询筛选、交易摘要及两端类型，不能直接对 null 调 getTime。
- Payment 保持现有短期有效期。支付尝试超时后查单/安全关渠道单，账单与订单继续待付；后续支付可以新建尝试。
- agency_service 不进入 closeExpiredOrders 的资源回收/账单作废逻辑；订单“取消支付”只关闭当前支付尝试，返回费用详情，不取消申请、不关闭应收、不将订单 fulfillmentStatus 置 cancelled。
- 首次收款确认后订单 fulfillmentStatus 设 ready，表示费用到账确认完成；用户界面显示“已缴费”，不显示“待使用”，更不能据此推导代办已完成。
- 本期不允许直接对 agency 账单调用通用作废、线下收款登记/复核接口，也不支持退款后重开同一账单。通用来源 API 应明确拒绝这些未支持操作。

撤回、驳回、补件和办结均不自动免除原应收；退款也不自动改变办理状态。办结后附件按已有保留策略清理，不删除费用关联、表单或资金记录。

## 4. 未付款改价：持久操作与并发控制

### 4.1 范围与状态

仅针对收费账单，amountFen 为正整数分，最多 100000000。Bill unpaid、paidFen=0、无成功付款、无待复核收款、无退款或人工核实事项时可申请改价。free 转收费、收费改零元和退款后再收费不属于改价。

新增 EnterpriseAgencyFeeChange（改价操作记录）：全局唯一 operationId、billId、expectedQuoteVersion、原/新金额、原因、操作人、请求摘要、涉及支付单、状态及重试信息。operationId 与 Idempotency-Key 一致；同键同摘要返回同一操作，异摘要 409。并发同账单最多一项活跃改价。

原因去首尾空白后 1–500 字符；金额与当前相同返回 400，不产生新报价版本或通知。数据库唯一约束/条件索引与锁共同保证单活跃操作，不能仅在应用层先查后建。

操作状态为 requested → closing → applied；另有 rejected（已确认不能修改）和 attention（渠道或本地结果不明）。activeChangeId 与操作记录在同一事务写入；未完成的操作不能靠超时清空冻结。

### 4.2 两阶段流程

1. **冻结事务**：锁 Bill，再锁关联 Decision/Order；检查 quoteVersion、资金条件及管理员权限，建立改价记录，editState=repricing。按固定锁顺序执行，所有资金入口统一以 Bill 为序列化根；申请受理先锁申请再锁 Bill，资金操作不得反向锁申请。
2. **渠道处理**：数据库事务外等待既有下单请求结束，再查询并关闭全部未终结支付尝试。查到已付，先确认资金事实，再将本次改价置 rejected；不更改金额。查关单超时、返回不明或存在未结束下单请求时置 attention，原金额不动，新支付继续冻结。
3. **应用事务**：渠道已证明所有旧尝试不可继续支付后，再锁 Bill 并校验操作 ID、版本、冻结状态和无收款事实；同事务同步 Bill/Order 金额、quoteVersion+1、快照变更历史，操作置 applied，Decision 恢复 stable 并清空 activeChangeId；写审计、用户可见改价记录及站内通知。rejected 与补偿结束的失败终态同样恢复 stable 并清空 activeChangeId，避免费用投影长期显示「正在更新」。改价记录持久化在 Change/账单历史，申请详情将其合并展示到时间线，不反向锁申请或覆盖申请 records，避免与受理/补件事务死锁。
4. **崩溃恢复**：补偿任务按原 operationId/Payment ID 继续查关单或完成应用事务；应用后的重放只返回已完成结果。只有确认未改价且旧支付状态明确时才可结束失败操作；不能以数据库回滚代替渠道关单。

### 4.3 下单与改价之间的屏障

仅在支付创建事务内检查一次冻结标志不足以防竞态：已创建本地 Payment 的线程可能在改价开始后才发起微信下单。要求所有代办渠道下单（含后台 Native）统一经过以下机制：

- 在 Bill 锁内登记下单命令、quoteVersion 和 dispatch 状态；冻结后不能登记或开始新的渠道下单。
- 下单命令以 Payment ID 唯一持久化（Payment 扩展字段或同 ID 一对一记录），至少含 quoteVersion、ownerToken、dispatchState、开始/结束时间及核实原因。queued → dispatching → launched；请求结果不明为 unknown，确认关闭为 closed。工作者在 Bill 锁内领取并登记 dispatching，后续接管不能靠租约超时将其当成未发起。
- 已开始的下单是持久的 in-flight 工作。改价必须等待其响应被记录，再执行查关单；后台恢复也不能在冻结期间重新派发旧下单。
- 渠道请求超时或进程失联不意味着渠道未收到请求；不得仅因租约过期、首次查单不存在或本地标记 closed 就放行改价。保持待核实，直到旧请求不会再创建可付款订单且查关单结果明确。
- 共享下单执行器必须跨实例串行化同账单下单/关单，登记、开始和结束受同一屏障约束；自动任务、管理员操作及用户请求都不得绕过。单进程 mutex 或只有客户端禁用按钮不合格。
- 改价最终提交再次检查无 in-flight/unknown 工作。旧版本客户端请求返回 409 PRICE_CHANGED，并返回刷新费用的指引；不能替用户默默接受新价。
- 回调/查单资金确认不被冻结阻断。若出现迟到付款，始终保留实际收款证据；与当前报价不匹配时进入 attention，由人工核对，禁止覆盖实际金额或再次收款。

实施前应为该屏障编写跨请求/跨进程时序测试。具体持久派发实现可复用现有基础设施，但上述顺序和恢复保证不可删减，也不能在长数据库事务内等待外部 HTTP。

## 5. 支付与退款

### 5.1 支付编排与版本

费用页使用已有上层 commerce 收银台；不新增仅按 billId 直接转发底层支付的入口。扩展 POST /api/app/commerce/orders/:id/payments，为代办要求 quoteVersion（正整数）；其他来源保持现有参数兼容。

服务端核对本人申请、Decision、Bill、Order 的完整一致关联及当前报价。只有来源、归属、版本、金额、渠道方法、AppID/绑定身份均兼容且状态可复用的 Payment 才能复用；attention、过期、正在改价和其他不明确结果不允许重复下单。收费到免费配置变化不影响已有应收。

- 微信内 Web：公众号授权绑定后 JSAPI。
- 外部移动浏览器：按 capabilities 使用 H5；桌面按既有能力使用 Native。
- 小程序：服务端按小程序 AppID 换取/核验绑定，走 wx.requestPayment，不接收客户端自报 OpenID。
- 授权回跳回原订单；回来后重新查询报价版本，变价必须重新确认。
- 取消调起、前端 success、页面返回都不直接记收款；使用通知/主动查询和现有恢复任务确认。

付款确认在事务内按实际 Payment 记录资金、同步 Bill/Order 并触发 agency_service 通知。重复通知与轮询不得重复累加。资金确认不能依赖申请仍 processing、服务仍开放或附件仍存在；异常应保留实际收款与人工处理信息。

### 5.2 代办部分退款（新增）

修正实际入口：POST /api/admin/commerce/payments/:id/refunds。增加幂等键与代办金额校验；审批/驳回/同步沿用 refunds/:id/approve、reject、sync。不能再引用不存在的 bills/:id/refund。

- 仅成功微信 Payment 可退款；运营填写 amountFen（正整数）与原因，另一位有退款审批权限的管理员审批。后台先取得成功 paymentId，不把 billId 当 paymentId。
- 为退款申请增加持久幂等键（退款记录的可空唯一 operationKey 或等效持久映射）；代办必填，摘要绑定 paymentId、金额、原因及操作者。不得仅在内存缓存请求结果；对其他来源保持原请求兼容。
- 在 Bill 锁内计算该 Payment 的占额：成功退款 + pending/processing/abnormal/attention 退款；rejected 和已确认 closed 不占额。新金额不得超过 payment.amountFen 减占额，且累计成功退款不得超过 Bill/Order 实收。
- 金额、幂等摘要、状态更新和占额必须原子校验。一个 Payment 同时最多一项非终结退款；上一项明确结束后允许下一笔。结果不明继续占额，不能新单重试规避；渠道调用与补偿始终复用原退款单号。
- 部分退款后 Bill 保持 paid，refundedFen 递增；全部退完 Bill=refunded。Order.paymentStatus 保留 paid 表示发生过实收；afterSalesStatus 表示本次待审/处理中/异常，全部终结后部分退为 none、全退为 refunded，累计金额用于独立展示部分退款，不能把部分退当成未付。
- 增加 agency 专用 onRefundRequested/onRefundRejected/onRefundResult 分支：不冻结/取消代办申请，不撤销表单或附件，不调用其他来源权益回收。Order.fulfillmentStatus 保持资金确认状态，不因退款设置 cancelled。拒绝通知不能使用“权益恢复”等不适用话术。
- 退款成功幂等更新 Bill/Order 累计、审计与用户通知；重新处理同一成功退款不再增额。退款失败/关闭恢复可退余额，异常/待核实不释放；用户界面同时显示累计已退与本次退款状态。
- 其他来源保持全额退款及既有权益处理规则，不因共享服务去掉全额判断而自动开放部分退款。
- 本期用户侧 orders/:id/refund-requests 对代办返回明确的“请联系社区处理退款”业务拒绝，交易详情不显示自助退款按钮；refund-requests/:id 只允许本人读取进度。
- 渠道支持范围、权限、退款期限及真实退款以实现时官方资料与商户验收为准。超期/渠道拒绝不能伪造成功；线下退款暂不写成微信退款。

已 paid 账单上若因屏障退化的极端场景发生同额二次渠道实收，Payment 置 attention 并保留资金事实；该状态无系统内退款出口（requestRefund 仅接受 success），由运营在商户平台按核对结果手工原路退回，处理记录补入账单备注与审计，不自动改写申请或资金累计。

已全退申请即使重提/再受理也不重新出账，页面显示原收款及全退历史。确需再次收费作为后续独立业务能力设计，不能用重复 businessKey 或清零累计退款绕过。

## 6. API、权限与开关

### 6.1 费用接口

以下为新增/扩展契约；静态 fee/fees 路由放独立控制器，避免被 :service 捕获或套用要求 :service 的守卫。

| 端 | 接口 | 约束 |
| --- | --- | --- |
| 用户 | GET /api/app/enterprise-services/fee?service=<route>&id=<applicationId> | 包含 registration，必须本人申请；返回下述统一费用投影 |
| 用户 | POST /api/app/commerce/orders/:id/payments | 复用上层编排；代办必传 quoteVersion，金额由服务端读取 |
| 用户 | GET /api/app/commerce/orders/:id、POST /api/app/commerce/payments/:id/sync | 本人结果查询，资金确认以服务端为准 |
| 后台 | 注册及三扩展服务 accept（§2.3） | 首次 manual 报价；已有决定不重新报价；配置版本及幂等键 |
| 后台 | PUT /api/admin/enterprise-services/fees/:billId | amountFen、reason、expectedQuoteVersion、Idempotency-Key；返回操作记录，未完成返回 202，完成返回 200 |
| 后台 | GET /api/admin/enterprise-services/fees、GET /api/admin/enterprise-services/fees/:billId | 分页/状态/服务/关键词；详情包含当前费额、改价和退款操作进度，精确关联申请 |
| 后台 | POST /api/admin/commerce/payments/:id/refunds | 代办部分/全额退款，财务权限与异人审批；其余来源仍全额 |

费用投影至少包含：serviceType、applicationId、feeMode、decisionStatus、billId/orderId（可空）、quoteVersion（可空）、amountFen（未决定为 null，已免费为 0）、paidFen、refundedFen、reservedRefundFen、title、refundPolicy、paymentStatus、afterSalesStatus、editState、canPay、blockedReasonCode、activeChange（本人可见摘要）。未受理的 feeMode 只表示当前配置参考，标记 estimated=true，不构成最终报价；正式决定后必须读取快照。

decisionStatus 为 pending_acceptance/free/quoted；未受理不返回 mode=pending_quote。已免费即使当前改为收费仍展示免费。支付状态使用 unpaid/confirming/paid/closed/attention；confirming 为派生态——存在已 launched 且未终结（无回调、查单未确认）的 Payment 尝试时显示，attention 仅来自异常实收或改价待核实；代办应收不自动变 closed，但保留历史支付尝试关闭状态。部分退款从金额推导，与退款操作状态分开。

未受理/免费时 billId、orderId、quoteVersion、paymentStatus 及 activeChange 为 null，paidFen/refundedFen/reservedRefundFen 为 0，canPay=false，分别使用 NOT_ACCEPTED/FREE 原因码；不能用 unpaid 表达“免费但还没付”。存在收费决定后，投影按同一一致性快照读取 Bill/Order/Decision 与退款占额，避免混合改价前后版本。

错误契约：越权/跨模块标识返回 404；未登录 401；已知资源无操作权限 403；非法金额/参数 400；状态、报价/配置版本、幂等摘要冲突 409。结果待核实返回稳定原因码，不返回可重复下单的假成功。所有响应沿用现有成功/错误包络。

幂等重放也必须先检查当前身份、资源归属和操作权限，再读取该操作者对应结果；不得通过猜测 Idempotency-Key 获取他人的操作响应。支付调起/取消当前尝试的渠道调用也加入 §4.3 屏障，不能在取消与重新下单竞争时关闭另一请求的新尝试。

### 6.2 权限与数据范围

- 用户：只能读/付自己申请的费用及其订单、Payment、Refund；不得通过 guessed billId、企业名或其他企业成员身份扩大范围。
- 后台费用控制器独立鉴权：先解析 Bill 的 agency 服务关联，再校验该服务既有菜单权限；聚合列表按可访问服务过滤，不能依靠前端筛选。改价另要求新增 perm:enterprise-agency:fee:reprice，既有角色不自动授予。
- 首次 manual 报价沿用该服务受理权限；退款仍要求 perm:commerce:refund:create/approve 与 commerce 数据范围，代办菜单权限不等于退款权限。
- 费用列表/改价使用 commerce 数据范围叠加对应服务权限；共享费用控制器显式检查该数据域，不能依靠当前未映射 enterprise-services 路径的 DomainScopeGuard 自动保护。普通申请详情保留现有数据域规则。
- 财务 commerce 账单可按 agency 查询最小资金资料，但不因有财务权限就开放完整表单/附件；无服务权限时不展示资料跳转。财务 Native 下单、作废/收款登记、交易列表/详情等通用入口都必须识别 agency 的并发屏障与能力限制。
- 用户可见事件与内部审计分离，日志/通知不包含密钥、身份证、原始材料或完整渠道响应。

### 6.3 功能与支付开关

新增 cashAgencyOpen（默认 false），只控制**发起新的代办支付尝试**。feeMode 控制定价，不代替业务开关或收款配置开关。

| 开关/场景 | 行为 |
| --- | --- |
| enterpriseAgencyOpen=false | 两客户端不显示企业代办入口；后台不显示企业代办菜单，新申请拒绝 |
| 单服务开关关闭 | 隐藏该服务新申请入口、拒绝新建；已有申请补件/重提和历史费用继续按既有契约处理 |
| cashAgencyOpen=false 或商户发起开关关闭 | 禁止新支付；查询、已发起渠道尝试的结果确认、关单、退款收尾不停止 |
| 已有费用而代办总开关关闭 | 通过“我的交易/账单”、已有通知及有权限的财务应收继续查询和缴费；缴费仍受 cashAgencyOpen 和商户发起开关控制，不恢复代办菜单 |
| 权限撤销/账号停用 | 新操作实时校验；系统查单、回调、退款补偿不依赖发起管理员会话 |

已有应收的支付可用性不由“是否允许新申请”决定。历史处理中申请仍可按授权直达详情；UI 隐藏不是接口鉴权。总开关、服务开关、收款发起开关、权限和快照分别处理，不能用一个布尔值替代。

## 7. 办理与资金关系矩阵

保持 pending/processing/needs_info/completed/rejected/withdrawn 六态规则：仅 pending 可撤回；needs_info、rejected、withdrawn 可重提至 pending；processing 不新增撤回能力。

| 场景 | 费用行为 |
| --- | --- |
| 从未受理 pending 撤回 | 无首次决定，无账单；重提后首次受理按当期配置 |
| 已免费受理后补件/驳回重提 | 沿用 free；以后改收费配置也不补收 |
| 收费受理后补件/驳回重提 | 沿用原 Decision/Bill/Order，不重新报价 |
| 已受理 → 补件 → 重提为 pending → 撤回 | 可以有原账单；保留应收/收款，不自动退款或关账 |
| processing 直接撤回 | 按既有规则拒绝，不能因收费模块改变办理契约 |
| 驳回 | 仍可重提；不自动免除应收或退款 |
| 办结但未付 | 原账单继续可缴费；办结不是免单，也不触发超时作废 |
| 已付款/部分退款 | 不允许改价；按剩余可退额度处理退款 |
| 全额退款后重提/再受理 | 保留同一历史单据，不重新收费 |
| 配置切换/服务暂停/附件已清理 | 不覆盖已形成的费用决定或资金事实 |

## 8. 两端与后台 UI

两端同构展示，移动 Web 为基线，小程序同步移植；组件落地前分别查询对应 TDesign MCP。

- 详情页“费用”区块区分未确认、免费、待付、确认中、已付、部分退、全退及待核实；改价期间显示正在更新，禁止发起支付。费用与办理进度并列，不以付款代替受理/完成。
- 用户付款前明确确认当前金额、标题、退款政策和报价版本；价格已变必须重新确认，不自动调起新价支付。改价展示前后金额及适合用户阅读的原因，历史政策不可静默覆盖。
- 复用完整收银台与交易详情，处理环境能力、未绑定、授权回跳、取消、返回、网络失败、确认中与主动刷新。没有支付能力时展示可执行说明。查询重试不创建新支付。
- 后台每项业务页用页内“办理申请 / 费用账单”选项卡；详情用“办理资料 / 费用与记录”分区，不为本次收费单独增加左侧菜单。既有财务应收增加 agency 筛选，避免重复建设财务列表。
- 改价弹窗含原额、新额、必填原因；提交中避免重复触发，202 后展示操作进度，可刷新恢复；后台关闭弹窗不取消服务端操作。
- 退款弹窗同时显示实收、累计已退、处理中占额、可退余额，默认不擅自填满全退；操作与审批权限分别呈现。用户不显示自助退款按钮，保留联系社区说明与退款进度。
- 全额退款不显示“待使用/待付款”，部分退款不把累计已退隐藏在单笔处理中状态里。尊重已有暗色/窄屏/字号、点击区、焦点、减少动画规则，长页必须滚动验收。

## 9. 通知、审计与补偿

首次报价、改价完成、到账、退款申请/审批结果/到账分别留痕。账单和订单持有当前快照，历史报价及改价操作不可覆盖；用户时间线不泄露内部备注。业务事务内保存站内通知，使用事件唯一键（类型+实体 ID+版本/终态）防重；推送若异步发送，使用事务性 outbox/现有等效持久机制，不把外部发送失败回滚成“未收款”。

现有支付、退款轮询复用；新增改价操作恢复、关联完整性检查及异常列表。补偿需要保证原单号重试、金额不重复累计，故障有可查询记录，不依赖前端长连接。收款成功但关联异常保留资金事实并标记待核实；禁止吞掉异常或让用户重新付一次。

## 10. 保留的业务决策与本次技术修订

| # | 原记录决策 | v3 保持方式 |
| --- | --- | --- |
| 1 | 未付款不阻塞受理与办理 | 办理六态与资金事实独立 |
| 2 | fixed 在受理时出账，重提不重复 | 首次受理事务生成 Decision/Bill/Order，合法再受理复用 |
| 3 | 支持未付改价，已付不可改 | 加入旧支付关闭、报价版本、持久屏障与补偿 |
| 4 | 企业注册纳入本期 | 注册独立 accept 与三扩展 accept 同时接入 |
| 5 | 单商户 | 复用 PaymentMerchantConfig，不做分账 |

本次设计选择：保留原稿退差额目标，将“代办部分退款”列为新增范围；采用两份业务元数据（费用决定、改价操作）承担唯一约束和恢复，不另建资金账本。以上是本次修订内容，不冒称新增用户拍板记录。

## 11. 实施拆分与回滚

1. **契约与迁移**：来源注册、Decision/Change 模型、金额/版本/身份契约、nullable 期限、权限和开关；历史受理单免费回填。先结构迁移，不立刻开放收费。
2. **受理与资金服务**：两个 accept、一次性出账、订单创建、报价事件与幂等；跨入口改价屏障、渠道关闭、持久补偿及到账/退款分支。屏障接入点须含三处既有关单路径：recover() 到期关单、closeExpiredOrders→closePendingForBill、用户取消；改价的批量关单不能直接复用 closePendingForBill（其仅处理最新一条），需循环全部未终结尝试；wechat-pay.client 预期无需改动。
3. **退款能力**：agency 部分退款、占额/异人审批、累计与进度、其他来源全额约束及权益回归。
4. **API 与两端**：费用投影、上层收银台、版本确认、所有交易列表/摘要/详情及退款可用性；后台页内分类与四组配置。
5. **隔离验证**：按 §12 跑矩阵与故障注入，各仓独立检查；生成接口/模型参考并检查根仓文档。
6. **发布准备**：先部署兼容 nullable 字段和新来源的消费者，再启用写入；旧客户端对未知来源提供安全展示/升级提示。默认四项 free、cashAgencyOpen=false，启用收费与发布必须另行决定。

回滚优先关闭新申请和支付发起，保留读接口、回调、查单/退款/改价恢复及原资金数据。产生新来源交易后不能直接回滚到不识别 agency_service 的旧版本；采用兼容性回滚/前向修复，不删表、不清库、不回收已记账事实。已有在途支付仍可到账，退款不因“暂停收费”停止。

## 12. 验收矩阵与完成门槛

| 类别 | 必测条件 |
| --- | --- |
| 四服务×三模式 | 两个 accept 接入点；首次免费/固定/人工；并发、重放、重复键异摘要 |
| 模式与历史 | 免费 → 补件重提 → 收费配置再受理仍免费；收费模式切换不覆盖；历史受理/记录缺失保守回填 |
| 改价竞态 | 用户/后台 Native 下单、下单 HTTP 在途、回调、查单、改价并发；支付成功拒改；旧版本确认拒绝 |
| 故障恢复 | 冻结后崩溃、渠道关单超时、未知下单结果、应用前/后崩溃、重复任务；不得跳过核实或出现第二次扣款 |
| 期限与状态 | Payment 到期再缴费；Order/Bill 无期限正确序列化及统计；完成后缴费；pending 有旧账单撤回；不新增 processing 撤回 |
| 退款 | 部分、多次、全额、余额不足、并发申请/审批、自己审批、拒绝、关闭、结果不明、重复成功；不改变代办状态 |
| 权限与旁路 | 跨用户/跨服务标识、菜单有权但财务无权、受限数据范围；通用支付、quotes/orders、作废、线下收款和自助退款接口不能绕过 |
| 开关 | 总/服务/现金/商户开关分别切换；入口和菜单隐藏；存量资金仍可查询、核实、退款；历史交易页可达 |
| 共享回归 | 商城、空间、活动、租约仍维持既有有效期、取消、整单退款及权益处理；nullable 字段不改变原来源行为 |
| UI 与渠道 | 两端登录状态、长页滚动、窄屏/暗色；微信内 Web、外部移动浏览器、小程序授权及取消/确认中/返回恢复 |

代码检查按各仓 AGENTS 执行；API 接口/资金变化必须使用隔离数据库、Redis DB>0 和独立上传目录。隔离测试、开发者工具、真实商户资金链路、两端视觉验收分别记录证据，不相互替代。真实渠道验收需覆盖实际收款、部分及全额退款、通知可达与异常恢复；未完成前不得声称收费模块或生产发布验收完成。

## 13. 复审记录

2026-10-31 已完成文档与当前源码契约的第二轮核对：原评审 R1–R10 均已有明确设计与验收要求，未发现仍阻塞实施的设计缺项，可按 §11 开始实施。逐项依据见[评审报告](enterprise-agency-fee-design-review-2026-10-31.md)的“v3 复审”章节。首轮意见保留为历史，不以新的行号覆盖原稿定位。

本结论是设计复审结果，不代表已具备新模型/接口、并发安全已由测试证明或真实渠道已验收。跨实例下单屏障、部分退款和共享模型兼容性是实施时重点验证项；验证失败时不得绕过条件开放收费。
