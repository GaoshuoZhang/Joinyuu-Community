# 企业代办收费设计 v2 评审意见

日期：2026-10-31。评审对象：[收费设计 v2](enterprise-agency-fee-design.md)。

> 版本说明：以下首轮意见及原行号对应修订前 v2，保留为历史记录。设计文件已修订为 v3；当前结论见末尾“v3 复审”，不是继续要求处理下方已在设计中关闭的事项。

结论：**建议修订后复审，当前不宜直接按实施清单进入开发。** 已记录的五项业务决策可以保留；主要问题在资金链路复用不完整、改价并发、超时关单和退款能力边界。本文仅提出评审意见，未修改原设计、业务代码或发布配置。

## 2. 阻塞实施的问题（P1）

### R1：仅创建账单不会进入新增的代办履约分支

**设计位置：第 19、65、83、89–97、131 行。**

设计只安排 accept 创建 `CommerceBill`，随后直接调用 `CommercePaymentService.appPayment`，却在 `CommerceFulfillmentService.onPaid` 上增加 `order.sourceType='agency_service'` 分支。现有履约首先按 billId 查 `CommerceOrder`，找不到就直接返回。因此按清单实施后，即使付款已确认，新增分支也不会执行，交易详情、站内信及售后关联都可能缺失。

源码依据：`apps/api/src/modules/commerce/commerce-fulfillment.service.ts:29`；订单与账单模型见 `apps/api/prisma/schema.prisma:191`。另外，后台 `COMMERCE_MODULES` 尚无 agency，客户端 `APP_SOURCE_TYPES` 尚无 agency_service，不能将通用列表和接口写成无需修改的“直接复用”。

**建议补齐：**明确账单与订单的一对一关系、订单创建/恢复时机、归属人、四类服务标识、金额与退款政策快照及 sourceLink；新增来源类型要同步 DTO、能力查询、支付开关映射、交易列表/详情和退款状态展示。可以受理时建立订单，也可以支付前建立，但必须在收款前保证关联存在。不要将代办生硬套用为租约订单。

**验收：**四类服务从受理到付款确认均能查询关联订单；重复回调只登记一次资金事实、发送一次到账通知；不改变代办办理状态。

### R2：只判断 unpaid 不能保证改价安全

**设计位置：第 83、85、108、124 行。**

用户已经生成 100 元支付单、尚未付款时，账单仍是 unpaid。后台改为 200 元后，现有 appPayment 仍会复用同方式且未过期的旧 Payment；支付确认以 Payment 的金额核验并写入账单，而履约以 Order 的金额更新订单。若只改 Bill，会出现仍付旧价，甚至账单与订单资金展示不一致。

源码依据：`apps/api/src/modules/commerce/commerce-payment.service.ts:64`、`:202`；`apps/api/src/modules/commerce/commerce-fulfillment.service.ts:29`。现有 `closePendingForBill`（同文件 `:307`）可作为复用基础，但关闭支付与写入新价之间还必须防止另一请求创建新支付。

**建议补齐：**改价先进入禁止新支付的状态或建立等效串行化机制，再查单/关旧单；已付款拒绝改价，结果不明保留原价并进入待核实。渠道确认关闭后，在事务中重查资金状态及报价版本，同步 Bill、Order 和展示快照，记录改价历史，解除阻止新支付。支付请求携带用户已确认的报价版本，版本变化要求重新确认；不可仅按“同账单未过期”复用旧单。存在待复核线下收款也应拒绝改价。

渠道依据：微信支付官方《关闭订单》本地同步副本 `APIv3/普通商户/支付产品/小程序支付/API列表/关闭订单-4012791901.md`，对应[官方地址](https://pay.weixin.qq.com/doc/v3/merchant/4012791901)。

**验收：**改价与创建支付、回调、主动查单、线下收款复核并发；旧单已付、关单超时、结果不明、重复改价与旧版本支付请求均不能产生错价或第二次扣款。

### R3：把支付过期等同于应收账单过期，会导致无法继续缴费

**设计位置：第 69、104、107 行。**

第 69 行说撤回不自动关账，第 104 行又称复用 expiresAt 自动关账。实际 `CommerceBill` 没有 expiresAt；有期限的是 Payment 和 Order。现有超时订单任务会调用 releaseUnpaid，除 lease_bill 外均将未付账单置为 void。直接给代办增加 Order 后沿用该机制，就可能让应收被作废，而唯一 businessKey 又不允许按重提新建另一张账单。

源码依据：`apps/api/prisma/schema.prisma:86`、`:127`、`:191`；`apps/api/src/modules/commerce/app-commerce.service.ts:1111`；`apps/api/src/modules/commerce/commerce-fulfillment.service.ts:251`、`:280`。

**建议补齐：**分开定义支付尝试有效期、收银台订单有效期、应收缴费期限。按现有“先办后付、重提复用”的决策，建议支付尝试到期仅安全关渠道单，应收继续保留；订单超时后能够在同一账单上恢复支付。明确人工作废、全额退款后再次重提是否继续有应收，不能让同一 businessKey 自动推导业务结论。

**验收：**受理后长时间不付款、完成后补付、补件重提、旧订单超时再支付；应收不被通用资源回收任务意外作废，也不重复出账。

### R4：已有退款仅支持全额，不能覆盖“多收退差额”

**设计位置：第 21、87、109、114 行。**

设计要求“完成后发现多收”与“部分退”，却写为直接复用既有退款链。当前 `requestRefund` 明确拒绝任何不等于原 Payment 金额的退款请求。另一个直接错误是文档列出的既有端点 `/api/admin/commerce/bills/:id/refund` 并不存在，实际申请退款是 `/api/admin/commerce/payments/:id/refunds`。

源码依据：`apps/api/src/modules/commerce/commerce-payment.service.ts:114`；`apps/api/src/modules/commerce/commerce.controller.ts` 的 refund 方法。

**建议补齐：**明确本期是否支持部分退款。若支持，必须列为共享资金能力扩展，包含金额上限、成功及处理中退款占额、异人审批、并发/拒绝/关闭后的可退余额、订单及账单累计退款、两端状态展示和已有业务回归；若不支持，就删除部分退与退差额承诺，写清只能整单全退。两种选择涉及范围差异，不能由实现者默默决定。修正退款路由及 paymentId 的获取方式。

**验收：**全退与差额退按最终选定范围分别验证；申请人不能审批自己的退款；重复通知/查询不会累加两次；不得超过已收金额。

### R5：免费首次受理没有持久快照，不能兑现“配置变化不补收”

**设计位置：第 46–47、65–67、76、110 行。**

快照目前只放在账单，而 free 明确不建账单。申请先按免费受理，之后补件重提为 pending，再在收费配置下受理时，没有记录能说明它已经按免费模式受理过，容易被补收。收费申请若重提时配置变更，manual 必填规则也可能再次要求报价，覆盖原有约定。

源码依据：`apps/api/src/common/enterprise-agency/service-runtime.ts:321`、`:524`，补件重提后会再次经过 accept。

**建议补齐：**首次受理就在申请的受控持久字段或结构化事件中保存费用决定，含 free、配置版本/时间、报价人及适用政策；不能只看账单是否存在。后续重提/再受理读取原决定，已有报价不再次要求 quoteAmountFen。此记录不必将付款状态塞入申请 payload，也不要求建立新的报价模型。

**验收：**free 首次受理 → needs_info → 重提 → fixed 配置下再受理仍免费；fixed/manual 首次受理后切换模式再受理保持原金额；并发 accept 只产生一次费用决定和账单。

### R6：将两端支付统一写为 JSAPI，会遗漏外部浏览器和小程序身份绑定

**设计位置：第 83、114、132 行。**

直接转发底层 appPayment 不等于复用了客户端收银台。当前上层 startPayment 负责订单归属、状态、模块开关及环境选择；移动 Web 按微信内/移动浏览器/桌面选择 JSAPI/H5/Native，小程序还要取得对应 AppID 下的用户绑定。只接受 billId 并固定 JSAPI，不能覆盖移动 Web 的正常外部浏览器场景，也可能遗漏小程序绑定与公众号授权回跳。

源码依据：`apps/api/src/modules/commerce/app-commerce.service.ts:729`、`:746`、`:759`；`:155` 的来源开关映射目前还会将未识别来源落到 cashLeaseOpen。

**建议补齐：**费用入口接入现有上层支付编排或抽出共享能力，保留环境识别、服务端绑定、capabilities、授权/绑定补偿、支付结果查询和返回路径；增加 agency_service 的明确开关映射。不得让代办支付误受租约开关控制，也不得由客户端任意提交 OpenID。所有“支付成功”以服务端确认结果为准。

**验收：**微信内 Web、外部移动浏览器、小程序分别覆盖未绑定/已绑定、取消支付、结果不明、授权回跳及主动查询恢复；没有渠道能力时解释原因，不展示无法执行的支付按钮。

## 3. 需要补齐的契约（P2）

### R7：企业注册没有被现有通用 accept 路由覆盖

**设计位置：第 31、84、125、131 行。**

文档只列 `/enterprise-services/:service/applications/:id/accept`。当前该控制器通过 extensionService 只识别 finance-tax、business-change、license，企业注册走 `/api/admin/enterprise-agency/registrations/:id/accept` 与独立 DTO/服务。因此按清单只扩展通用入口会漏掉已明确纳入本期的注册。

源码依据：`apps/api/src/common/enterprise-agency/service-runtime.ts:21`、`:69`；`apps/api/src/modules/enterprise-agency/enterprise-agency.controller.ts:26`、`:56`。

**建议：**分别列出两个 accept 接入点，共享费用决定/出账服务，但保留各自校验、事务与权限。四类业务都纳入 fixed/manual/free 和再受理回归。

### R8：新费用接口缺少可执行的归属、权限与停用规则

**设计位置：第 82–87、115、130–133 行。**

当前代办动态权限守卫要求 :service，拟新增的 `/fees` 和 `/fees/:billId` 没有该参数，直接加入原控制器会因无法解析服务而失败；若为绕过此问题移除守卫，又没有按账单对应申请重新鉴权的方案。用户端底层 appPayment 只接 billId，也不能承担用户归属校验。

源码依据：`apps/api/src/modules/enterprise-services/enterprise-services-permission.guard.ts:15`；`apps/api/src/modules/commerce/app-commerce.service.ts:565` 的订单归属；退款接口分别要求 `perm:commerce:refund:create` 与 `perm:commerce:refund:approve`。

**建议：**明确本人申请与账单/订单归属关联；跨账号及跨模块 billId 查询/支付返回不可见。后台费用列表按可访问服务过滤，单据详情/改价再次鉴权；退款保留财务权限和异人审批，不因有代办菜单权限就自动获得退款权。补齐数据范围与审计目录。

总开关关闭后按既有要求隐藏客户端入口和后台菜单；单服务关闭新申请后，历史费用查看、待付账单、查单/回调、退款如何收尾需要明确，不能因菜单隐藏而停止资金补偿任务。收费模式 free 是定价策略，不能替代功能开关或支付发起开关。

### R9：撤回/驳回矩阵与当前六态契约冲突

**设计位置：第 69、103–107 行。**

当前只有 pending 可撤回；rejected、withdrawn、needs_info 都可重提。设计却直接列“受理后撤回”和“驳回（不可重提失败）”，未说明是否调整办理状态规则。pending 也未必从未受理：已受理 → 补件 → 重提后就会回到 pending，并保留原账单。

源码依据：`apps/api/src/common/enterprise-agency/service-runtime.ts:128`、`:289`、`:321`；注册撤回限制同样见 `apps/api/src/modules/app/enterprise-agency/enterprise-agency.service.ts:210`。

**建议：**矩阵按“是否已有首次受理费用决定/账单”与当前办理状态分别描述，保留现有撤回与驳回重提规则。若确实新增 processing 撤回或终态驳回，应单独列为业务变更，不能夹带在收费模块中。

### R10：费用查询没有足够状态支撑稳定收银台

**设计位置：第 35、66、82–83、114 行。**

mode 既表示 free/fixed/manual，又返回 pending_quote，混淆定价策略与报价进度；免费显示还被绑定到“当前配置”，会与首次受理快照冲突。§2 写人工报价在受理后填写，§3 又要求受理时必填。现有 fee 响应没有订单/报价版本及支付结果不明、退款处理中等明确契约，客户端难以正确刷新与恢复。

**建议：**明确人工报价发生在受理动作内；将 feeMode、费用决定状态、支付状态、售后状态分开，返回 orderId、quoteVersion 与可支付性/不可支付原因，快照决定免费文案。至少定义未受理、已免费受理、待支付、支付确认中、已付、退款审批/处理中、全退、结果待人工核实；部分退取决于 R4 最终范围。改价前后保留用户所见政策与版本，重新确认新金额后再支付。零元改价/免单是单独业务语义，不能在正金额支付链路里含混处理。

## 4. 建议的修订顺序与验收门槛

1. 先修订 R1/R3：画清申请、费用决定、账单、交易订单、支付尝试、退款的关系及各自有效期，明确关联键、归属与金额真源。
2. 修订 R2/R5：写出首次受理、再受理、改价与支付竞争的事务边界、报价版本及补偿流程。渠道 HTTP 调用不得被描述为数据库事务可以整体回滚。
3. 明确 R4 的部分退款范围，再修正路由和费用/退款响应状态。
4. 补齐四类 accept 入口、上层收银台复用、权限/开关与存量资金收尾规则，更新 P1–P5 实施拆分。
5. 测试计划除原有矩阵外，必须点名覆盖：免费首次受理后改配置再受理；有旧支付时改价；改价与建支付并发；超时后继续补付；注册入口；跨账号/跨服务越权；服务停用后的回调退款；退款金额边界及共享商城/空间/活动/租约回归。

上述设计缺口关闭后可进入实施；真实商户收款、退款、真机及视觉验收仍是独立发布门槛。本次不因代码已有通用组件就宣布收费模块可以验收。

## 5. 核对后未列为问题的事项

- `agency:<申请ID>` 当前没有证据表明跨服务会撞键：四类编号分别使用 EA、TE、BR、LA 前缀。可以增加 serviceType 以强化关联表达，但不应将其误报为已存在的编号冲突。
- 保留六态办理状态、不以付款阻塞受理/完成、受理时出账、未付可改价、四类服务纳入、单商户等既有设计方向，本次不要求重新决策。修订目标是让它们能够被现有资金模型正确实现。

### 6.3 第二轮检查发现并补齐的边界

- **下单已登记但 HTTP 尚未执行**：不能仅检查冻结一次；补上下单持久派发状态、跨实例屏障、unknown 不自动解冻的要求。
- **后台/通用端点旁路**：Native 与用户支付共同遵守屏障；代办不得被 bills/:id/orders 转成租约，不得走未支持的线下收款、作废或用户自助退款入口。
- **部分退款误取消办理/权益**：明确 agency 专用退款分支，部分和全退都不改变申请，且其他来源仍保持原全额退款规则。
- **锁顺序反转**：受理先申请再 Bill；资金操作不再反向锁申请，改价时间线由 Change/账单历史投影，避免直接覆盖申请 records。
- **历史数据与空期限兼容**：费用决定回填不追溯收款；nullable 字段同步迁移、API、统计和两端类型；旧客户端部署顺序与回滚边界写入实施计划。
- **免费状态、幂等越权与退款重放**：无账单状态返回 null/0 而非 unpaid；重放先鉴权；退款有持久幂等约束；同额改价不制造版本与通知。

### 6.4 实施风险与下一步

设计通过不消除实现风险。优先实现并验证跨实例下单/改价屏障与部分退款占额，随后接两端与后台 UI；nullable 模型变化必须带共享商城、空间、活动、租约回归。不能仅完成费用卡片就宣称收费模块完成。
