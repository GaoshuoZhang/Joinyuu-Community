# 聚屿社区仓库拆分计划

日期：2026-10-29。状态：本地拆分已按此方案实施，实际结果见 [迁移记录](repository-split-report.md)；业务远程仓库尚未配置。

## 目标与推荐方案

保留 `D:\Projects\Joinyuu-Community` 作为统一工作目录，将后端 API、管理后台、移动 Web、微信小程序变为四个独立业务仓库。继续沿用现有 `apps/` 路径，减少文档、启动工具和开发者工具项目路径的变动。

建议将现有根仓库逐步转为轻量协作仓库，管理工作区说明、联调工具和整套产品的发布清单。因此最终是 **四个业务仓库 + 一个协作仓库**。协作仓库沿用当前仓库，不需要再创建一个业务项目。

```text
D:\Projects\Joinyuu-Community\
├── .git/                         # 原仓库，转为协作仓库
├── .gitignore                    # 忽略四个业务仓库目录
├── AGENTS.md                     # 工作区地图、跨仓操作规则
├── README.md                     # 总入口、安装与联调说明
├── repositories.json             # 路径、远程地址、默认分支
├── releases/                     # 产品发布组合：各仓版本、tag、commit SHA
├── scripts/                      # 克隆、状态汇总、启动、跨端联调
├── docs/                         # 跨端架构、联调、整套部署与发布说明
├── .agents/skills/               # 现有本地技能保留，维持其本地属性
└── apps/
    ├── api/                      # 独立仓库：Joinyuu-API
    │   ├── .git/
    │   ├── AGENTS.md
    │   ├── docs/
    │   ├── pnpm-lock.yaml
    │   ├── package.json
    │   ├── prisma/
    │   ├── src/
    │   └── test/
    ├── admin/                    # 独立仓库：Joinyuu-Admin
    │   └── .git/ ...
    ├── client-mobile/            # 独立仓库：Joinyuu-Client-Mobile
    │   └── .git/ ...
    └── wxminiprogram/            # 独立仓库：Joinyuu-WXMiniProgram
        └── .git/ ...
```

仓库名仅为建议，远程仓库尚未创建。四端分别在自己的仓库根目录提交、拉取、打 tag 和发布。

如果严格要求总共只有四个 Git 仓库，也可把父目录作为普通文件夹，将原仓库完整归档到工作目录之外；代价是父目录的协作说明和工具需要另外安排版本管理。本计划优先推荐保留协作仓库。

## 必须解除的依赖

### 安装、构建与运行

- API、后台、移动 Web 各自维护 `package.json`、锁文件、ESLint 配置、Node/pnpm 版本约定、README 和检查命令。
- 根目录不再用 `pnpm-workspace.yaml` 将四个业务仓库纳入一个安装单元。根目录可以保留只负责委派命令的 `package.json`，但不提供子仓的构建依赖。
- 将根 `pnpm-workspace.yaml` 中仍需要的构建脚本许可和平台设置逐仓核对、迁移，不直接丢弃 Prisma/esbuild 等安装行为配置。
- 从现有锁文件中尽量保留各端的已解析版本，再生成各仓锁文件并核对版本差异。拆仓和依赖升级分开实施。
- 小程序第一阶段保留现有 npm 与 `package-lock.json`，单独处理 ESLint 8 配置和 npm 构建流程，避免同时更换工具链。
- 两个 Web 端移除 `@joinyuu/shared-web: workspace:*`，分别内置 favicon 工具，保留其现有行为和验证。共享代码明显增加后，再评估独立的版本化包。
- 改写三个本地 `.bat`：在对应子仓执行命令，不再引用父目录 `node_modules/vite`。
- 审查小程序的模板 `.github/` 工作流与包元数据，去掉不适用的模板发布流程，保留许可证及来源信息。

验收原则：把任一业务仓库单独克隆到工作目录之外，在没有父目录依赖的环境下，仍能完成其安装、检查和构建。

## 统一 Agent 工作方式

父目录继续作为统一工作入口。根 `AGENTS.md` 要明确四个业务仓库的路径、必读文档、运行命令和 Git 边界；各子仓也必须拥有自己的 `AGENTS.md`，保证单独打开时可以工作。

根规则应明确要求：

1. 开始任务先定位涉及哪些仓库，分别读取对应子仓规则并检查工作树状态；从父目录启动时，主动读取相关子仓 `AGENTS.md`。
2. 搜索业务代码时显式进入对应子仓，避免父仓 ignore 规则使默认搜索漏掉代码。
3. Git 命令指定仓库，例如 `git -C apps/api status` 和 `git -C apps/admin diff`。
4. 跨仓需求分别检查、分别提交，通过任务编号或发布清单关联提交。一次根仓提交不会包含四端修改。
5. 根规则不要要求始终同步所有端版本；改接口时检查受影响消费者及兼容性。
6. 将本地技能留在现有父目录位置；只给确实需要独立工作能力的仓库补充必要技能入口，不依靠自动扫描兄弟目录。

OpenAI 文档说明，主要工作目录用于默认 Git 操作和项目配置发现，附加目录可以读写；PR 和 worktree 操作针对主要仓库。因此，**统一目录访问不能等同于四仓 Git UI、PR 和 worktree 自动统一**。官方来源：[Projects and chats](https://learn.chatgpt.com/docs/projects)。

对当前偏好的使用方式，优先在父目录以 Local 模式协同开发，并显式操作各子仓。实施验收应实测从父目录搜索、修改、检查四端的体验；若需要在应用审查面板中稳定显示各仓，可在同一个项目中附加子仓目录，无需建立四个独立项目。

根协作仓库的 worktree 不会自然包含被忽略的四端仓库。单仓 worktree 必须从目标业务仓库创建；需要隔离整个产品时，应由专门的工作区初始化工具在新目录检出发布清单指定的四仓版本。

Codex 自动读取规则沿项目根到当前工作目录查找，不应假定从父目录启动就已读取全部子仓规则。来源：[AGENTS.md instructions](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## Git 结构与历史迁移

默认采用独立 clone + 仓库清单管理。当前规模下先不引入 submodule；如果后续更看重 Git 原生锁定子仓提交，可另行采用 submodule，但仍需处理独立依赖和测试耦合。

API、后台、移动 Web 使用 `git filter-repo` 在临时的新克隆中提取各自目录历史，让原 `apps/<端>/` 的内容成为新仓根目录。源仓库保留完整历史；根配置和分配的文档再作为迁移提交加入各目标仓库。历史路径曾迁移过的文件需单独审查。参考：[GitHub 拆分子目录指南](https://docs.github.com/en/get-started/using-git/splitting-a-subfolder-out-into-a-new-repository)。

过滤后的 commit SHA 会变化；源仓标签、分支、Issues、PR 和发布记录不能视为已经整体迁入。记录源仓基线 SHA 与各新仓初始 SHA 的对应关系，并明确迁移哪些分支和标签。

小程序沿用现有独立历史，不从根仓提取。建议把模板远程保留为 `upstream`，将自己的新仓设为 `origin`，并在推送前核对目标地址。

四端完成独立验证且历史已备份后，根仓再停止跟踪原来三个业务目录，并增加针对四个目录的 ignore 规则。该步骤只改变根仓的跟踪关系，保留磁盘上的独立业务仓库。仅写 `.gitignore` 不会使已跟踪文件自动退出根仓索引，见 [Git ignore 文档](https://git-scm.com/docs/gitignore)。

根仓克隆完成后，使用 `repositories.json` 与初始化脚本克隆业务仓库；脚本遇到已有目录或已有 `.git` 时必须校验身份并保留当前修改，不能覆盖。

## 版本与发布

迁移验证期间保留现有已发布版本。完成拆分后，建议各仓独立维护语义化版本及 CHANGELOG，同时由协作仓库记录经过联调的产品组合。

发布清单至少包含产品发布标识、四仓 tag/commit SHA、接口契约版本、数据库迁移要求、部署顺序和回滚说明。只记录分支名无法复现某次发布。

新增接口保持兼容，通常先发布后端，再发布消费者。删除字段或改变状态含义采用分阶段迁移，尤其要考虑已经安装或仍在审核中的小程序客户端。

仓库拆分不要求立刻把部署基础设施全部重建。第一阶段主要调整代码来源、安装/构建目录和启动命令；后续各端再独立优化发布流水线。

## 实施顺序

1. **建立可恢复基线。** 分别记录根仓和小程序仓的状态、分支、远程与 SHA。保存未提交修改、新增文件、被忽略的本地配置及小程序 `.git`。Git bundle/clone 不包含未提交文件及被忽略文件，不能作为唯一备份。确定当前微信登录等在途改动的快照归属。
2. **先在原结构解除工程耦合。** 将 favicon 工具内置、移除测试跨仓源代码读取、纳入主题 fixture、修复小程序图标脚本依赖。先验证这些改动，再进入历史拆分。
3. **在临时目录建立新仓。** 分别提取 API、后台、移动 Web 历史，补齐独立配置和文档；小程序保留现有历史。此阶段不覆盖正在使用的工作目录。
4. **完成独立安装与验证。** 每仓在工作目录之外单独克隆验证，确认不会回退到父目录 `node_modules`。各仓 CI 只检出自身也能完成必要检查。
5. **建立协作入口与远程。** 创建并核对四个业务仓库的目标远程，准备根规则、仓库清单、初始化/状态汇总/启动工具，改写整体部署说明。
6. **切换本地目录。** 在服务停止后，将已验证的新仓放回原 `apps/` 路径，恢复必要本地配置和运行数据；再让根仓停止跟踪业务代码。通过文件清单和哈希核对迁移结果。
7. **整套联调与发布。** 验证四端连接同一 API，记录首个四仓组合清单，更新版本规则并完成实际部署路径验收。

## 运行数据与回退

拆仓只迁移代码及开发资料，不重建数据库、不更改既有迁移记录。独立迁移时保护以下本地或部署数据：API `.env`/`.env.it`、上传目录、客户主题、支付配置加密主密钥及证书、小程序私有项目配置，以及现有 PostgreSQL/Redis/MinIO 数据卷。

Docker Compose 的项目名和实际数据卷名在实施前记录，切换后保持或显式映射；改变启动位置可能让 Compose 选择另一组卷。所有安装、路径和脚本验证均不得通过重置生产或日常开发数据库完成。

旧工作目录和完整历史在验收前保留独立备份。回退代码时使用迁移前快照；如果已执行新的数据库迁移，按数据库备份和兼容性单独处理，不能把代码回退视为数据库回退。

## 完成标准

- 四个业务仓库拥有独立 `.git`、正确远程、完整安装配置与说明；能分别提交、构建和发布。
- API 单仓可完成 Prisma generate、类型检查、lint、构建、单元测试及隔离数据库 e2e。
- 后台单仓可完成类型检查、lint、UI 测试和构建；移动 Web 单仓可完成类型检查、lint（含排版检查）、组件测试和构建。
- 小程序单仓可完成依赖安装、npm 构建、静态检查和开发者工具编译；测试脚本不再保留模板的占位失败命令。
- 四端从父目录统一启动/访问，后台与两种客户端的关键登录、查询和写入流程通过联调；支付、微信登录等在途功能按迁移时实际范围另列结果。
- 根仓仅管理协作内容，业务修改分别出现在对应子仓；父目录入口下的 Agent 能定位并检查所有业务仓库。
- 从全新目录只克隆协作仓库，运行初始化工具即可恢复四仓布局；固定发布清单可恢复指定版本组合。
- 原始历史、未提交内容、本地配置和运行数据均可核对、可恢复，当前部署保持可用。
