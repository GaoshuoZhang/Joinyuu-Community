# 社区政策版本冲突修复

日期：2026-10-15。

## 根因

`Policy_published_kind_version_key` 原来约束所有已发布记录的 `(kind, version)` 唯一。社区政策统一使用 `kind = community`，因此不同政策填写同一版本号（例如 `1.0`）也会触发 Prisma `P2002`。

原统一异常过滤器把此错误作为 500 打印“未捕获异常”；该日志本身不是 Node 进程退出的证据。

## 修复

1. 新迁移 `20261015183000_scope_policy_versions_to_agreements` 将唯一索引范围收窄到已发布的用户协议、隐私协议。社区政策是独立文档，可以使用相同版本号。迁移在事务中先创建新索引再删除旧索引，不删除或修改政策内容。
2. 平台协议新增和编辑增加版本预查，编辑时排除自身；归档记录允许同版本共存。数据库继续处理并发兜底，创建和更新中的版本冲突均转换为明确的 409 提示。
3. 统一错误过滤器识别 Prisma 唯一字段冲突，返回可读的 409，不再按 5xx 故障输出堆栈。SQL、冲突值和数据库内部信息不会返回给客户端。系统生成主键冲突及其他未知故障仍保持 500 和故障日志，避免掩盖内部错误。
4. 同类检查发现通知模板保存采用“读取最大版本再加一”，事务内仍存在并发窗口。保存、发布、下架现在共用模板父记录的 `SELECT ... FOR UPDATE` 锁；发布目标也在锁内读取，防止版本号碰撞及发布状态交错。

## 同类问题检查范围

检查了 Prisma schema 与手写唯一索引，以及政策/协议、通知模板、通知渠道、用户、管理员、角色、字典、办公区域和办公位的创建与更新路径。

用户用户名/昵称/电话/邮箱、管理员账号、角色编码、字典名称、办公区域名称、办公位编号和通知配置等入口，即使预检查与写入之间发生并发冲突，现在也有统一的 409 兜底。已有业务服务中的明确冲突提示继续保留。其余业务约束没有擅自放宽。

## 当前环境状态

修复前确认当前开发库没有其他待执行迁移。本次仅应用上述新增索引迁移；`prisma migrate status` 已确认 78 条迁移全部应用。数据库为 API 当前 `.env` 指向的本机 PostgreSQL `joinyuu`，未进行 seed/reset，也未执行其他环境的部署。

收尾时发现 7757 未监听，且原项目的开发监听进程残留、没有服务子进程。已停止这个确认属于本项目的失效监听进程，并以单个 `pnpm dev:api` 开发进程恢复服务；API 健康检查及经 7758 后台代理的健康检查均返回 `status: ok`。

其他环境发布此修复时，需要同步执行 `prisma migrate deploy`；只更新 TypeScript 服务代码不能消除旧索引对社区政策的错误限制。
