# 离线许可证管理

入口：后台「系统管理 → 系统配置 → 许可证管理」。使用现有 `/system/config` 权限和 system 数据范围，不新增菜单权限。未导入许可证、缺失/错误的公钥、错误签名、错误产品或部署实例、尚未生效均显示「许可证无效」。有效期采用 UTC ISO 8601 时间，页面按北京时间展示；到达 `expiresAt` 的瞬间视为已到期，无宽限期。依赖服务器时钟，不能抵御主机管理员修改程序或回滚虚拟机快照。

## 授权格式

签名算法 Ed25519。外层仅有 `payload`（原始 UTF-8 JSON 字节的 base64url）和 `signature`（签名 base64url）。校验原始字节，不重新序列化 JSON。授权字段仅允许：

| 字段 | 含义 |
| --- | --- |
| version | 格式版本，固定 1 |
| productId | 固定 joinyuu-community |
| licenseId | 许可证编号 |
| customerId / customerName | 客户编号、名称 |
| deploymentId | 部署实例标识 |
| keyId | 信任公钥标识 |
| issuedAt / notBefore | 签发时间、生效时间 |
| expiresAt | 使用截止时间，null 为永久有效 |
| updatesUntil | 历史格式兼容字段，签发工具固定为 null，界面不展示 |

所有非空时间使用 `2027-10-14T00:00:00.000Z` 格式。无功能模块、账号数/社区数限制、签发序号。许可证不加密，不应包含秘密信息。

## 日常签发：双击并输入天数

后端已内置供应商公钥，不再读取 `LICENSE_PUBLIC_KEYS_FILE`。客户服务器不需要配置公钥路径，也不需要签发工具或私钥。本次复用已有 `vendor-2026` 密钥，没有重新生成或替换私钥。

独立 Windows 工具目录：`D:/JoinyuuSigning`。签发工具和私钥不属于项目仓库。

1. 在后台「系统管理 → 系统配置 → 许可证管理」填写客户名称，下载授权申请文件。
2. 把 `license-request-xxxx.json` 放进工具目录，与 `*.private.pem` 同级。
3. 双击 `生成许可证.bat`，输入授权天数，如 `365`。
4. 工具会在同目录创建以客户名称命名的文件夹，将所选授权申请文件、`.license` 和 `许可证信息.txt` 放进去。把 `.license` 发给客户，在许可证管理页面导入；申请文件和信息文本留作签发记录。

工具自带 `runtime/node.exe`，不需要安装 Node.js、pnpm、项目依赖，也不需要联网。请保留完整工具文件夹。启动脚本自动进入自身目录；多个申请文件或私钥时按编号选择，不会自动取第一份。

有效期从**本次签发时刻**开始计算，每天为完整 24 小时。输入必须是 1–36500 的整数，空值、负数、小数均会提示重输；起止时间按北京时间展示。客户编号默认使用 `customer-部署标识`（同一部署续期保持一致），许可证编号自动生成 UUID。交互工具只签发按天的有限期授权；底层仍兼容历史永久许可证。

文件名使用申请内容中的部署标识，不信任输入文件名；同名许可证或申请文件存在时自动追加签发时间，绝不覆盖旧文件。`许可证信息.txt` 每次追加完整签发信息，包括对应的许可证与申请文件名。续期可直接选择客户目录中已归档的申请文件，也可将新申请放入工具根目录。客户名称中不适合作为 Windows 文件夹名的字符会被替换并附加短哈希，避免路径越界和重名。签发前检查私钥是否匹配内置公钥，签发后自验签。申请不合法、私钥不匹配、缺少文件、输入中断均不会生成许可证。`vendor-2026` 只是已内置公钥的内部 `keyId`，用于选取验签公钥，与许可证有效期无关。

## 开发与打包

公钥的唯一源码位于 `apps/api/src/common/license/license-public-keys.json`，由 `trusted-keys.ts` 作为固定信任表导入并随 API 构建发布，不允许用环境变量或上传的许可证覆盖。以后更换密钥，更新这份公钥表，保留必要的旧 keyId，重新构建/发布后端，再打包签发工具。程序更新前不会信任新公钥。

独立签发工具仅保存在 `D:/JoinyuuSigning`，不在项目的 `tools` 目录中维护副本。它包含 `issuer.cjs`、`生成许可证.bat`、`使用说明.txt`、公钥副本与独立运行时。项目内仅保留后端内置公钥及其验签逻辑。以后更换密钥时，需同步更新后端内置公钥和外部签发工具的公钥副本。

工具文件夹中的 `license-public-keys.json` 只是签发时用于核对的公钥副本，不是客户服务器的部署配置。不要把整个工具目录交付客户；仅交付 `.license` 文件。私钥必须离线备份并通过操作系统权限限制访问；公钥不能恢复私钥。

现有部署更新：完成数据库迁移（如此前未应用）、重新构建并重启 API，即可使用内置公钥。之前配置的 `LICENSE_PUBLIC_KEYS_FILE` 可删除，即使保留也不会生效。

## 状态与只读边界

- 正常：业务写入正常。
- 已到期 / 许可证无效：全局 LicenseGuard 拒绝非 GET/HEAD/OPTIONS 的业务请求，覆盖后台和移动端。已有 RBAC 和身份校验保持生效，不会因许可证例外放行越权请求。
- 显式维护例外：后台/客户端登录登出，密码修改/找回，后台会话强制下线，个人数据导出，授权申请与许可证导入。注册、绑定手机号/邮箱、配置修改、上传、审核、批处理和业务写入均受限制。
- 查询、CSV 导出继续工作。导出所需的文件生成、通知和审计，以及登录会话、验证码和安全日志属于维护写入，允许执行。
- SchedulerService 的所有注册任务在只读状态下跳过；文章详情不累加浏览量，企业查询不落库更新邀请/负责人转移的过期状态。电子票允许读取已存在的票，尚未签发的票不会在查询时新建，而是提示许可证限制。
- 数据库/文件的运维备份不受应用许可证影响。项目目前没有内置备份接口，本次不新增备份产品功能。
- 每个写请求/任务检查当前有效期，不使用长效授权缓存；页面每 30 秒刷新状态，后端校验不依赖页面刷新。已获准执行的进行中操作不被强行中断。

新增接口时：只读查询不得产生业务写入；任何必要的维护 POST 必须显式使用 `@LicenseMaintenance()`，并补充权限和只读回归测试。新增后台执行入口也须检查 LicenseService，不能只依赖 HTTP Guard。

## 续期、备份与迁移

续期使用原申请文件或同一部署重新下载的申请，输入天数后签发并导入，无需重启。有效期从本次签发时刻重算，不自动叠加旧许可证剩余时间。不支持在线吊销，也不基于签发序号防旧证重放。

DeploymentLicense 表保存单例部署标识、签名文件和导入时间；生成申请不重置部署标识。数据库和对应程序版本一起备份；容器更新不改变标识。恢复数据库会恢复原绑定。独立的新部署应生成新的部署标识并重新申请，不要把生产数据库克隆当作新授权。部署 ID 是逻辑绑定，不具备防整机克隆能力。

## 验证

`pnpm --filter @joinyuu/api test:unit` 包含签名、篡改、过期边界、永久授权、未知公钥及字段格式测试。`test/license.e2e-spec.ts` 在隔离测试库检查无授权登录/查询/导出、权限保护、导入、审计、只读任务和续期恢复。

现有 e2e 的 `reseed()` 在检查数据库后缀 `_it`/`_test`、NODE_ENV=test 和独立 Redis DB 后，生成短期真实签名测试许可证及临时公钥。测试私钥不落盘；仅 Jest setup 将信任表替换为临时测试公钥（E2E_LICENSE_PUBLIC_KEYS_FILE），生产应用完全不读取此变量，也不添加免授权逻辑。独立工具可在其目录执行 `runtime/node.exe --test issuer.test.cjs`，测试使用临时密钥文件并在结束时清理。
