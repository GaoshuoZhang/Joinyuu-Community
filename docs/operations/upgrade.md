# 升级与回滚

升级对象是独立业务仓的固定提交和产物，不能仅拉取协作仓就认为四端已更新。以根仓 releases 清单记录的兼容组合为依据；先在隔离环境验证，再按迁移要求安排生产窗口。

## 升级前

1. 记录根仓与四端当前 commit、版本、运行配置和部署路径。
2. 备份 PostgreSQL、上传/对象存储、许可证记录、客户主题、环境配置以及支付加密主密钥；确认备份可恢复。私有配置单独受控保存，不提交 Git。
3. 阅读 API 的 Prisma 增量迁移和 [版本日志](../releases/api.md)，检查数据转换、约束、兼容性与不可逆操作。保存当前 Web dist 与 API 构建产物。

## 更新与启动

分别 fetch 所需业务仓，检查工作树干净后检出经过验证的目标 commit/tag。不要覆盖本地配置与数据目录；不要使用 git clean -fdx 清理部署目录。

API 仓执行 `pnpm install --frozen-lockfile`、`pnpm build`；在正确生产环境配置下执行 `pnpm db:migrate`，再由既有进程管理器重启 `pnpm start`。start 自带 migrate deploy。多实例由部署流程协调迁移与重启，不能把开发种子作为修复迁移问题的手段。

后台和移动 Web 各自安装锁定依赖并 `pnpm build`，原子替换产物或切换部署目录后重启 `pnpm serve`。维持 API_PROXY_TARGET、端口和数据挂载。小程序需独立构建、体验版验证和正式发布，兼容尚未更新的旧客户端。

## 验收

核对健康接口返回的 API 版本、两端关于页版本、静态资源与深链接、代理、登录权限、上传和关键业务状态。跨仓版本不同是正常现象。支付及其它外部服务按各自验收记录检查，不能将本地 mock 测试记为真实收款。

## 回滚

先判断新迁移是否仍兼容旧代码。若兼容，恢复旧 commit/依赖/产物并重启相关服务；不能默认数据库会随代码自动降级。若不兼容，使用已评审的修复迁移或数据库恢复方案；恢复旧备份会丢失备份后的写入，必须明确业务处理与停机窗口。

数据库恢复需同步恢复对应上传存储和原支付主密钥。切回旧 Web 后仍应保证 API 兼容已发布小程序。完成后再次验证版本、健康、权限与关键业务，并记录实际回滚范围。
